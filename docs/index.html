Dataset size

messages (the events in the feed)
from about transactions ·

Messages grow in proportion to cards × days (about 2.9 per card per day by default). Merchants do not change the count; they only spread the same purchases over more shops (below about 100 merchants some purchases are skipped). The levers below move it a little: refunds, reversals, chargebacks, duplicates and fraud add messages, and declines remove clearings. Estimates of message counts were checked against real runs and land within about 3%. Big runs are cut into groups of cards (about 250,000 messages each) that generate in parallel and stream to disk, so memory stays small and size is limited by disk. The 10-million preset was run for real: 5.5 minutes, 3.7 GB.

Which kinds of fraud the compromised cards produce. Only the ratios matter; a weight of 0 turns a pattern off.

Operational incidents

Incidents are time-boxed events with known causes (issuer outage, latency spike, storm, rule change, release bug). They are written to incidents.json. There is no industry percentage for them; they exist so a monitor has something to find.

Your own incidents

Place any of 12 incident types anywhere in the run: pick a type, a target, when it starts and how long it lasts. The prepared five above have fixed times; these do not. Each one is written to incidents.json with the ID INC-C1, INC-C2 and so on, and applies even if the prepared ones are switched off.
